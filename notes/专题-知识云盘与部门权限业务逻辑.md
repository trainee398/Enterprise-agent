# 业务学习专题：知识、企业云盘与部门权限

> 更新日期：2026-09-14。依据本轮开发环境的页面与接口实测，以及用户补充整理。本文描述业务对象、业务流程和访问规则，不代表后端源码或数据库模型分析。
>
> **前端交互后续还会调整。** 页面布局、按钮名称、入口位置和操作步骤不作为固定设计；学习时重点理解资料属于谁、内容如何保存、模块如何衔接、谁有权访问。

## 1. 先理解三部分分别管理什么

| 部分 | 管理对象 | 主要业务动作 |
| --- | --- | --- |
| 知识 | 分类、知识条目、知识历史版本 | 创建、阅读、修改标题和正文、保存、搜索、移动分类、查看历史、归档 |
| 企业云盘 | 文件夹、上传文件、导出文件 | 上传、预览、下载、移动、删除、恢复，以及转为知识 |
| 部门与权限 | 部门、员工归属、空间访问范围和读写权限 | 建立部门、分配员工、允许本部门操作、限制跨部门访问、随调部门更新权限 |

知识和云盘分别管理内容。云盘上传成功只说明文件已保存；将文件转成知识是另一个业务动作。知识分类和云盘文件夹也分别存在，不能因为名称相同就视为同一个位置。

## 2. 业务对象之间的关系

```text
员工 ──所属部门──→ 部门空间
员工 ──当前访问权限──→ 企业空间

每个已验证的空间中：
  知识：分类 → 知识条目 → 当前内容与历史版本
  云盘：文件夹 → 文件（文件夹可包含二级文件夹）

云盘文件 ──转知识──→ 新知识条目
知识条目 ──导出到云盘──→ 文件（本轮验证了 DOCX）
```

“空间”表示资料的归属和访问范围；“分类”“文件夹”表示在该范围内如何整理资料。部门名称用于显示，内部部门 ID 用于区分部门。名称相似不应导致不同部门合并。

本轮验证了部门空间和企业空间，未把其他空间类型或更细的权限组合写成已确认能力。

## 3. 知识的业务逻辑

### 3.1 创建与保存

一条知识需要明确所属空间、分类、类型、标题及内容。具备编辑权限的员工可以创建 Markdown 知识，也可以创建思维导图、甘特图等类型。

```text
确定资料归属及知识类型
  → 创建内容
  → 保存标题和正文
  → 再次读取已保存内容
  → 后续修改并保存
```

以上是业务关系，不限定界面上先填标题还是先编辑正文。本轮验证了 Markdown 正文与标题修改后的保存、重开一致性；思维导图和甘特图仅验证创建、保存及再次打开。

已保存内容可以查看历史版本。本轮能读取修改前的正文；历史恢复、保留期限以及多人同时编辑规则尚未验证，不能将“能看历史”理解为这些能力也已通过。

### 3.2 整理与找回

- **切换分类**：改变当前查看的资料集合。本轮切换后返回，已保存正文保持一致；未保存编辑的保护规则仍需单独确认。
- **移动知识**：改变条目所属分类。本轮在同一部门空间内移入另一分类再移回，正文保持一致；跨空间移动不在本次结论内。
- **搜索知识**：本轮标题搜索可找到目标知识，不能据此承诺全文搜索的覆盖范围。
- **删除/归档**：业务上用于退出正常使用范围；当前知识及空分类归档失败，尚不能作为可正常使用的完整流程。

知识分类的多级结构未在本轮确认；云盘支持二级文件夹不代表知识也支持二级分类。

## 4. 企业云盘的业务逻辑

### 4.1 文件保存与使用

```text
在有权限的空间建立文件夹
  → 上传文件
  → 查看文件及预览内容
  → 下载原文件
  → 按需移动文件位置
```

本轮 MD、TXT、DOCX 样本都完成了上传、预览及下载，下载内容与上传一致。云盘支持本轮验证的一级和二级文件夹，文件移动后内容保持一致。

文件删除后可以恢复，本轮使用独立临时文件完成了删除、恢复及下载核对。没有验证永久删除、保留期限或全部文件格式。

云盘中的文件管理和知识正文编辑是不同业务。本轮确认了上传、移动等文件管理动作，未确认云盘支持直接在线修改文件正文。

### 4.2 云盘与知识之间的衔接

| 业务动作 | 本轮实际结果 | 应如何理解 |
| --- | --- | --- |
| MD 转知识 | 生成知识条目，正文与文件文本一致 | 可作为可编辑知识正文使用 |
| TXT 转知识 | 生成知识条目，正文与文件文本一致 | 可作为可编辑知识正文使用 |
| DOCX 转知识 | 生成条目并保存附件记录，但正文为空，阅读时未展示附件 | 当前衔接不完整；不能描述成已成功转换为可读正文 |
| 知识导出到云盘 | 生成 DOCX 文件，可预览和下载 | 是一次导出结果，本轮未验证其他导出格式 |

原 DOCX 在云盘中可以正常预览，故“云盘预览正常”和“转知识后可读”必须分别判断。当前失败不等于原文件丢失。

本轮没有验证源文件修改后自动更新知识，或知识修改后自动覆盖已导出的文件。学习文档不将这些操作描述成双向实时同步，也不再沿用“所有上传文件都会自动转成 Markdown”的概括。

## 5. 部门与权限的业务逻辑

### 5.1 部门、员工与资料归属

管理员建立独立部门，将普通员工分配到部门。员工按照当前归属和权限访问对应空间中的知识及云盘内容。

以测试数据为例：研发员工管理研发资料，销售员工管理销售资料；同名分类、同名文件夹可以分别位于不同部门空间，它们不因此成为共享资料。

### 5.2 当前已验证的访问规则

| 身份与范围 | 已验证的业务结果 |
| --- | --- |
| 普通员工在本部门空间 | 可创建分类和知识、编辑知识、创建云盘文件夹、上传和移动文件 |
| 销售员工访问研发空间 | 读取、搜索、查看历史、修改知识，以及查看云盘、预览、下载和移动文件均被接口拒绝 |
| 普通员工在企业空间 | 能读取测试知识及云盘列表；修改企业知识、创建分类和云盘目录被拒绝 |
| 管理员在企业空间 | 本轮可创建企业测试分类及知识，供普通员工只读访问 |

该表对应本轮账号配置，不能推导为所有角色和权限组合都已验证。跨部门访问经过直接接口验证，访问限制不只依赖界面隐藏。

### 5.3 员工调部门

```text
调整员工部门归属
  → 原登录会话访问旧部门资料被拒绝
  → 可以读取新部门测试知识
  → 调回原部门后恢复原部门访问
```

本轮研发员工临时调入销售部后，旧会话访问研发知识和云盘立即被拒绝；调回后恢复访问。这里验证的是员工访问范围变化，未验证或假定资料会随人员调动自动迁移。

## 6. 学习时要区分正常规则与当前缺陷

| 应理解的业务规则 | 当前已发现的缺陷 |
| --- | --- |
| 每个部门应有独立身份，新建部门不应覆盖已有部门 | `QA_研发部`、`QA_销售部` 默认创建都生成 ID `QA`，第二次覆盖第一次名称；不是“中文前两个字相同” |
| 知识与空分类应能完成当前提供的归档动作 | 归档失败，对象仍保留 |
| 转知识成功后，应有可读取的正文或附件 | DOCX 转知识后正文为空，附件未在阅读页面展示 |

为继续验证隔离，测试研发部已改为显式指定独立 ID；这只是测试数据处理，不代表部门创建缺陷修复。三个缺陷均不应写成产品的正常业务规则。

## 7. 用一份资料串起来

研发员工在研发部云盘上传会议记录 TXT，可以预览和下载；将它转成知识后，可以修改知识标题、正文并保存，查看旧版本，也可以在本部门分类之间移动。销售员工不能通过接口读取这份研发资料。需要文件形式时，研发员工可将知识导出 DOCX 到云盘。

这个例子串联了本轮分别验证过的业务动作，不表示曾用同一份 TXT 完成全部步骤。学习重点是：**空间决定资料归属，权限决定能做什么，分类和文件夹负责整理，知识保存与文件导出分别产生各自的结果。**

前端交互后续还会调整。只要业务规则没有另行变更，入口合并、步骤减少或页面改版，都不应改变上述内容一致性和访问边界。

## 8. 学习核对与依据

可以用以下四个问题检查理解，不新增产品测试任务：

1. 上传云盘成功，是否等于已创建可读知识？为什么 DOCX 要分别判断？
2. 分类切换、知识移动、修改正文，分别改变了什么？
3. 两个部门创建同名分类，为什么不代表内容共享？
4. 员工调部门，访问范围变化是否等于资料自动搬迁？
