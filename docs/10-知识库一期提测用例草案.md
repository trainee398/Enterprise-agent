# 文档 10 · 知识库一期提测用例草案（文档管理范围）

> 版本：kb-phase1-cases-2026-09-08-draft  
> 状态：草案，尚未在产品环境执行  
> 依据：[当前范围记录](00-知识库一期范围与待确认事项.md)、[竞品报告](../企业Agent知识库竞品调研与Markdown一期设计建议.md)；早期文档 8 仅借鉴契约确认与留证方法  
> 范围：一期文档管理模块。主线是上传 → 转换成 MD → 检查 → 修改 → 维护；直接新建是次线。Agent 接入、RAG 问答、引用溯源不在本轮。

## 0. 这份文档解决什么问题

文档 8 和原 `test-datasets/` 用例按“上传 → 切片 → 提问 → 引用”设计：53 条旧用例含 Retrieval 14 条、Answer 20 条、生命周期 12 条、UX 7 条。按当前整理口径，一期先做文档管理；34 条检索/回答与旧 UX 中的提问、引用、Chunk 设置三条不直接用于本轮。已有语料和上传思路可复用，编辑保存及日常维护用例需按当前范围选择。

本文是候选测试清单。**先确认功能是否本期提供，再使用对应 P0/P1 排序；这些优先级不是领导或研发已经承诺的功能清单。** 下表的“code”只说明适合用接口或脚本判定，不代表自动化已经实现。

领导最新目标是容易上手、先做好一个点。当前建议验证“打开就能放资料，不用先想怎么分类”；该具体切入点和默认归属方案仍待确认。

### 0.1 首轮先走的一条流程

静态原型先观察第一行；拿到可操作版本和已支持样本后再执行全流程。

| 顺序 | 任务 | 记录什么 | 对应用例 |
| --- | --- | --- | --- |
| 1 | 首次进入，不讲解，找到上传入口 | 犹豫位置、误点、求助次数；是否理解保存位置与可见范围 | UX-001、008 |
| 2 | 上传一份已支持格式，等待并打开 | 上传和处理状态是否真实；转换后的内容是否完整可读 | UP-001 或对应格式用例、UX-002 |
| 3 | 修改一处正文、保存、关闭后重开 | 修改保留、保存反馈真实、原文件没有被回写 | ED-001、002 |
| 4 | 返回首页，通过最近资料或已支持的搜索找回 | 能否找到同一份已修改的文档，归属是否符合预期 | SR-001、002（按范围）、UX-009 |
| 5 | 制造一次确认可复现的上传或保存失败 | 不虚报成功；错误可理解；知道下一步，输入按承诺受保护 | UP-006 或 ED-003、UX-003 |
| 贯穿 | 用对应身份核对实际提供的访问入口 | 默认归属不扩大权限，未授权者不能获得内容 | PERM、SR-004（按入口） |

记录首次点击上传的耗时、前置选择数、完成情况和求助情况，先建立观察基线，不预设未经讨论的秒数门槛。若未采用默认归属方案，就记录实际选择步骤，不能把“必须无选择”直接报为缺陷。

更完整的目录、版本、回收站、导出与协作候选见第 3 节，按已确认范围另行启用。

## 1. 提测前先向开发确认的契约

拿到 build 之前先把这些问清楚。没确认的项标“待确认”，不要把产品没承诺的能力测成缺陷。

| 项目 | 需要确认 | 影响的用例族 |
| --- | --- | --- |
| 首次使用与默认归属 | 是否采用少做前置选择的方案；默认保存位置和可见范围；是否需要先选库 | UX、DIR、PERM |
| 支持格式 | `.md` 是否为核心；`.docx`、`.txt` 是否在一期；PDF/图片/Office 其他格式是拒收还是仅存附件 | UP |
| 大小与数量限制 | 单文件大小、单次批量上传数、库容量 | UP |
| 处理方式 | 同步还是异步；离开页面任务是否继续；失败能否单独重试 | UP、UX |
| 状态枚举 | 是否采用 等待 / 上传中 / 转换中 / 已完成 / 完成但有内容需检查 / 失败；“需检查”由什么触发 | UP、UX |
| 转换保真承诺 | `.docx` 哪些结构承诺保留（标题层级、列表、普通表格、图片），哪些明确不保证（合并单元格、批注、修订、页眉页脚） | UP |
| 图片与资源 | 图片是随正文持久化还是引用外链；导出时是否打包 | UP、EXP |
| 编辑范围 | 源码 / 工具栏 / 预览三者是否都有；是否允许多人同时编辑；冲突策略是提示还是锁 | ED |
| 保存方式 | 自动保存还是手动；保存失败如何提示；未保存内容是否本地保留 | ED |
| 更新语义 | 同名重传是覆盖、并存还是询问；“更新此文档”是否生成新版本；转换失败时旧版本是否保留 | VER |
| 版本与恢复 | 历史保留多久；恢复是否留记录；来源文件是否可下载 | VER |
| 目录模型 | 目录层级上限；删除目录是否连带；跨库移动是否允许 | DIR |
| 搜索范围 | 是否搜正文；是否分词；修改后多久可搜到；是否只返回有权限的内容 | SR |
| 权限模型 | 库级还是文档级；角色是否为 阅读 / 编辑 / 管理；搜索、历史、附件下载、导出是否按同一套权限过滤 | PERM、SR、EXP |
| 回收站 | 保留期限；恢复到原位置还是根目录；彻底删除是否可操作 | RB |
| 导出 | 单篇导出 MD 是否在一期；带图片时给资源包还是只给链接；整库导出是否一期 | EXP |
| 审批流 | 是否有必须沿用的发布或审批要求 | ED、PERM |

可观测性字段（只争取本期已实现能力对应的字段）：`upload_id`、`document_id`、`conversion_job_id`、`source_file_id`、`version_id`、`directory_id`、`status` / `error_code` / `error_detail`、`created_at` / `converted_at` / `modified_at`、`actor`。没有 `version_id` 和 `conversion_job_id` 时，版本恢复和部分失败重试两类用例只能靠界面判定，要记为可测试性风险。

## 3. 一期候选用例清单

执行前给每条用例标记“已纳入本期 / 待确认 / 不适用”，并记录确认来源和适用版本。只有已纳入的用例才进入该版本验收分母；待确认和缺前置条件不能算通过。

| 用例范围 | 启用条件 |
| --- | --- |
| UP | 使用已确认支持或明确拒收的格式；批量、资源、结构、编码各按承诺选择 |
| ED | 已提供编辑；自动/手动保存、编辑锁或版本冲突按实际策略判定；新建入口单独确认 |
| DIR | 已提供对应库、目录或移动能力；默认位置与当前目录区别说明 |
| SR | 按已确认的搜索范围、字段与生效延迟执行 |
| VER、RB、EXP | 分别确认版本/更新、删除/恢复、导出能力后启用 |
| PERM | 角色按实际模型映射；检查所有已提供的访问路径；没有某入口记不适用，不虚报已测 |
| UX | 首次使用观察可先做；默认归属方案、多个库、设置页等按实际页面选择 |

以下结果描述是判定建议；实际策略的等效实现也可成立，例如锁定编辑与提示版本冲突都能防止静默覆盖。

编号规则 `KB1-<族>-<序号>`。判定方式：code 指可用脚本或接口字段判定，manual 指人工观察。“对应旧用例”指可直接改写的 KBV1 编号。

## 5. 状态模型建议（按产品确认后映射）

下表是内部判定参考，不要求首页同时展示所有状态、字段或短暂中间阶段。用户主要需要知道能不能打开、是否成功、出错后怎么办。

| 状态 | 用户能做什么 | 可观测字段 |
| --- | --- | --- |
| 等待 | 取消 | `status=queued` |
| 上传中 | 取消；看进度 | `status=uploading`、`upload_id` |
| 转换中 | 离开页面；不能打开正文 | `status=converting`、`conversion_job_id` |
| 已完成 | 打开、编辑、移动、导出 | `status=ready`、`document_id`、`converted_at` |
| 完成但有内容需检查 | 同“已完成”，另有核对入口和问题清单 | `status=ready_with_warnings`、`warnings[]` |
| 失败 | 查看原因、重试、删除 | `status=failed`、`error_code`、`error_detail` |

文档编辑态另有 保存中 / 已保存 / 保存失败 三个状态，只出现在编辑页，不与转换状态混用。

## 6. 缺陷分层

用户说“内容不对”时，按这个顺序定位，避免把转换问题报成编辑器问题：

1. 转换层：原文件 → MD 的差异。证据：原文件、转换后 MD、`conversion_job_id`、警告清单。
2. 存储与版本层：保存、历史、恢复、更新语义。证据：`document_id`、`version_id`、时间线、两次读取的正文 diff。
3. 目录与搜索层：归属、移动、索引更新、权限过滤。证据：`directory_id`、搜索请求与结果、账号角色。
4. 权限层：五条访问路径的实际返回。证据：账号、请求、响应码、是否泄露片段。
5. 前端状态层：状态文案、刷新一致性、离开提示。证据：截图 / 录屏、刷新前后状态。

## 7. 执行顺序

1. **范围确认**：结合第 1 节和范围记录 C01–C09，记录版本、已承诺能力、账号、样本与可获得的证据；逐条选择候选用例。
2. **首次使用观察**：原型阶段先做 UX-001 和 UX-008 的理解观察，不产生上传/保存通过结论。
3. **首轮主线**：有可操作版本后执行第 0.1 节流程，使用最少的代表性样本；状态、内容和权限随流程一起核对。
4. **配套验证**：从 UP、ED、DIR、SR、VER、RB、PERM、EXP、UX 中执行已纳入本期的用例，补充异常、恢复与边界。
5. **回归留证**：失败项附最短复现、原文件、转换正文/保存结果、实际状态及账号；修复后复测。真实结果写入 `test-datasets/runs/<build>/`。

每条执行记录包含：用例 ID、适用性及确认依据、产品版本、样本/账号、预期、实际、证据路径、状态、问题与回归结果。状态使用待确认、未执行、不适用、阻塞、通过、失败，分别统计。

## 8. 验收建议的使用边界

- 已纳入本期的上传打开、编辑保存重开、找回主线应逐条验证；删除恢复只在已提供并纳入范围后作为对应链路验收。
- 已确定权限下的全部已提供入口均检查，不因界面简化而跳过；已发现泄漏和虚报成功作为阻断问题提出。
- 已纳入本期的高优先级用例通过后，才能报告该范围的测试结论。未通过项保留失败状态；若负责人决定带问题发布，记录接受人、影响范围与处理计划，不把 known issue 改成通过。
- 格式、结构、编码和资源保真按确认承诺判定，未承诺能力标明限制或待确认；不能用支持上传代替可编辑正文转换。
- 上手体验先记录首次操作、前置选择、误点、求助和完成情况，再讨论可接受目标；不虚构统一秒数或满意度分数。
- 本文仍是草案；没有真实执行记录前，不报告产品通过率或“可以上线”。
