# 文档 10 · 知识库一期提测用例草案（文档管理范围）

> 版本：kb-phase1-cases-2026-09-07-draft  
> 状态：草案，尚未在产品环境执行  
> 依据：《企业知识库竞品调研与 Markdown 文档管理一期建议》§7.1、§8、§9.1；文档 8 §2 最小契约  
> 范围：一期文档管理模块。主线是上传 → 转换成 MD → 检查 → 修改 → 维护；直接新建是次线。Agent 接入、RAG 问答、引用溯源不在本轮。

## 0. 这份文档解决什么问题

文档 8 和 `test-datasets/` 是按“上传 → 切片 → 提问 → 引用”的 RAG 知识库设计的：53 条用例里 Retrieval 14 条、Answer 20 条，UX 里也有提问、引用、Chunk 设置三条。领导已确认一期只做文档管理，这 34 + 3 条一期用不上，而转换保真、编辑保存、目录、搜索、版本、回收站、权限、导出这些一期真正要验的，旧清单里基本没有。

本文做三件事：说明旧资产哪些复用、哪些冻结；给出一期用例族和清单；列出要新做的测试文件。

## 1. 提测前先向开发确认的契约

拿到 build 之前先把这些问清楚。没确认的项标“待确认”，不要把产品没承诺的能力测成缺陷。

| 项目 | 需要确认 | 影响的用例族 |
| --- | --- | --- |
| 支持格式 | `.md` 是否为核心；`.docx`、`.txt` 是否在一期；PDF/图片/Office 其他格式是拒收还是仅存附件 | UP |
| 大小与数量限制 | 单文件大小、单次批量上传数、库容量 | UP |
| 处理方式 | 同步还是异步；离开页面任务是否继续；失败能否单独重试 | UP、UX |
| 状态枚举 | 是否采用 等待 / 上传中 / 转换中 / 已完成 / 完成但有内容需检查 / 失败；“需检查”由什么触发 | UP、UX |
| 转换保真承诺 | `.docx` 哪些结构承诺保留（标题层级、列表、普通表格、图片），哪些明确不保证（合并单元格、批注、修订、页眉页脚） | UP |
| 图片与资源 | 图片是随正文持久化还是引用外链；导出时是否打包 | UP、EXP |
| 编辑范围 | 源码 / 工具栏 / 预览三者是否都有；是否允许多人同时编辑；冲突策略是提示还是锁 | ED |
| 保存方式 | 自动保存还是手动；保存失败如何提示；未保存内容是否本地保留 | ED |
| 更新语义 | 同名重传是覆盖、并存还是询问；“更新此文档”是否生成新版本；转换失败时旧版本是否保留 | VER |
| 版本与恢复 | 历史保留多久；恢复是否留记录；来源文件是否可下载 | VER |
| 目录模型 | 目录层级上限；删除目录是否连带；跨库移动是否允许 | DIR |
| 搜索范围 | 是否搜正文；是否分词；修改后多久可搜到；是否只返回有权限的内容 | SR |
| 权限模型 | 库级还是文档级；角色是否为 阅读 / 编辑 / 管理；搜索、历史、附件下载、导出是否按同一套权限过滤 | PERM、SR、EXP |
| 回收站 | 保留期限；恢复到原位置还是根目录；彻底删除是否可操作 | RB |
| 导出 | 单篇导出 MD 是否在一期；带图片时给资源包还是只给链接；整库导出是否一期 | EXP |
| 审批流 | 是否有必须沿用的发布或审批要求 | ED、PERM |

可观测性字段（对应文档 8 §2.2，按新范围替换）：`upload_id`、`document_id`、`conversion_job_id`、`source_file_id`、`version_id`、`directory_id`、`status` / `error_code` / `error_detail`、`created_at` / `converted_at` / `modified_at`、`actor`。没有 `version_id` 和 `conversion_job_id` 时，版本恢复和部分失败重试两类用例只能靠界面判定，要记为可测试性风险。

## 5. 状态模型（与报告 §8.3 一致）

| 状态 | 用户能做什么 | 可观测字段 |
| --- | --- | --- |
| 等待 | 取消 | `status=queued` |
| 上传中 | 取消；看进度 | `status=uploading`、`upload_id` |
| 转换中 | 离开页面；不能打开正文 | `status=converting`、`conversion_job_id` |
| 已完成 | 打开、编辑、移动、导出 | `status=ready`、`document_id`、`converted_at` |
| 完成但有内容需检查 | 同“已完成”，另有核对入口和问题清单 | `status=ready_with_warnings`、`warnings[]` |
| 失败 | 查看原因、重试、删除 | `status=failed`、`error_code`、`error_detail` |

文档编辑态另有 保存中 / 已保存 / 保存失败 三个状态，只出现在编辑页，不与转换状态混用。

## 6. 缺陷分层

用户说“内容不对”时，按这个顺序定位，避免把转换问题报成编辑器问题：

1. 转换层：原文件 → MD 的差异。证据：原文件、转换后 MD、`conversion_job_id`、警告清单。
2. 存储与版本层：保存、历史、恢复、更新语义。证据：`document_id`、`version_id`、时间线、两次读取的正文 diff。
3. 目录与搜索层：归属、移动、索引更新、权限过滤。证据：`directory_id`、搜索请求与结果、账号角色。
4. 权限层：五条访问路径的实际返回。证据：账号、请求、响应码、是否泄露片段。
5. 前端状态层：状态文案、刷新一致性、离开提示。证据：截图 / 录屏、刷新前后状态。

## 7. 执行顺序

- 第 0 轮（半天）：拿到 build，按 §1 逐项确认契约；准备 §4 文件集；核对可观测字段是否拿得到。
- 第 1 轮（P0 主线）：UP-001~012 → ED-001~007 → VER-001~006 → RB-001~004 → DIR-001~005 → SR-001~006 → EXP-001~004 → PERM-001~005 → UX-001~005。权限用例放最后但必须做完，它是其他族的共同验收条件。
- 第 2 轮（P1 与体验）：其余 P1 用例；找 2~3 位不了解实现的同事做 UX-007；列表观感单独收集。

## 8. 一期提测门槛建议

- 主线三条链路 100% 通过：上传 → 已完成 → 打开正文一致；修改 → 保存 → 重开一致；删除 → 回收站 → 恢复完整。
- PERM 族 0 泄漏；SR-004、SR-005 必须通过。
- P0 用例全部通过，或每条未通过项有开发确认的 known issue 和修复版本。
- 状态假成功（显示已完成 / 已保存但实际未落地）为阻断级缺陷。
- 转换保真按 §1 确认的承诺范围判定；未承诺的结构损失记为“需检查”提示是否到位，不记转换缺陷。
