> 整理日期：2026-09-08。依据本次对话中的补充和已有文档整理；这是工作口径记录，不是已评审的 PRD。后续口述确认和版本范围在这里更新。

## 1. 哪些信息来自哪里

| 信息 | 来源与状态 | 如何使用 |
| --- | --- | --- |
| 目前没有正式需求、产品文档，主要依据领导口述后自行整理 | 用户明确补充 | 文档中的分析和建议不自动升级为产品承诺 |

| 首页突出上传、搜索和最近资料，整理入口按需展开 | 为上述体验点提出的原型建议 | 不等于已定产品结构，也不代表已完成开发 |

## 2. 当前要解决的任务

用户有一份已有资料，希望放进系统，打开核对，修正内容，之后还能找到继续维护。

```text
放入一份已支持的文件
    → 明确看到处理中、完成或失败
    → 打开转换后的正文，必要时核对原文件
    → 修改并保存，重开内容仍在
    → 通过最近资料或搜索找回
```

建议先打磨开始前的体验：打开页面就知道怎样上传，减少先建库、选目录、填标签的准备。清楚的状态、内容完整、保存可靠和正确的访问范围，是这条流程可信的基础。

直接新建空白文档作为次要入口。模板、复杂目录、批量整理等按实际需要评估；RAG 检索、问答、引用、Agent 绑定和主动跟进留在后续材料中。

## 3. 简化页面与能力范围怎么分

| 层次 | 当前建议 | 确认边界 |
| --- | --- | --- |
| 首页首先展示 | 上传资料、搜索、最近资料，轻量显示保存位置与可见范围 | 先验证易用性；搜索范围和默认位置还要确定 |
| 打开文档后展示 | 正文、编辑/保存反馈、需要核对时的来源入口 | 保存方式、编辑形式和来源访问按产品确认 |
| 需要时展开 | 移动、分类、新建库、来源详情、版本、导出、回收站等入口 | 这里只讨论呈现方式，功能是否本期交付另行确认 |
| 所有流程共同遵守 | 不虚报成功、不静默丢内容、不误覆盖、不扩大已确定权限 | 不能因首页简化而省略可靠性与权限校验 |

“首页少几个入口”与“后台是否实现这些能力”分开讨论。默认知识库属于库级归属，当前库的根目录属于库内位置，两者不能直接等同。默认归属方案也不意味着默认全员共享。

## 5. 文档之间以什么为准

1. 当前范围与信息来源看本文；有新口述时先更新来源与确认状态。
2. 竞品能力、个人体验和设计参考看[调研报告](../企业Agent知识库竞品调研与Markdown一期设计建议.md)。这次整理没有重新核查外部产品资料。
3. 出图看[原型方向与提示词](11-知识库一期原型方向与图片生成提示词.md)，图是方案示意，不是产品已实现的截图。
4. 测试看[一期提测草案](10-知识库一期提测用例草案.md)。P0/P1 是候选用例的建议优先级，先确认适用性，再纳入版本验收。
5. 已有测试文件和缺口看[测试资产入口](../test-datasets/README.md)。用例设计完成、文件存在、数据集冻结、产品测试通过分别记录。

文档 01–07 与课程笔记承载长期 Agent 学习；文档 08–09 和原 Retrieval/Answer 集承载早期 RAG 预研。保留这些投入，后续接入时按届时的接口与规则重新评审。
