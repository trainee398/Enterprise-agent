## 0. 先给结论

### 0.1 有开源集，但没有一套覆盖完整产品链路

公开资源已经覆盖了不少局部问题：

```text
文档版面 / 表格 → 检索 → 长文证据 → RAG 接地与幻觉 → 更新/删除
```

但几乎没有一套公开数据同时包含：

```text
Web 上传交互 + 处理状态 + Parser + Chunk + Embedding + Vector DB
+ 权限/版本生命周期 + Agent 上下文使用 + 引用 + 首次使用体验
```

所以本项目采用“三层组合”：

1. **开源基准**：校准检索、文档理解和回答可信度，避免指标完全自说自话。
2. **自建受控语料**：作为 V1 发布门槛，精确覆盖支持的文件类型和关键业务事实。
3. **线上 bad case 回流**：发布后持续补齐真实错误，形成长期回归集。

### 0.2 对当前 V1 的直接建议

- 不要先下载一个大型 benchmark，再把它当成产品测试计划。
- 先确认 V1 实际支持的文件类型；如果只有文本型 PDF/DOCX/TXT，优先自建可核对文档，不要为了“覆盖 OCR”引入图像数据集。
- 先用 8–12 份受控文档和 40–60 个黄金问题跑通链路，再接入少量 BEIR、DocVQA/TAT-QA、RAGTruth/RGB 等资源做专项校准。
- 开源数据的平均分不能替代企业门槛：答案能否回到正确 Chunk、数字是否准确、无依据是否拒答，必须有本项目自己的真值。

## 1. 按测试层整理的开源资源

### 1.1 检索 / Embedding 基准

| 资源 | 覆盖内容 | 对本项目的用途 | 不能替代什么 | 优先级 |
| --- | --- | --- | --- | --- |
| [BEIR](https://github.com/beir-cellar/beir) | 多种公开语料、查询和 qrels，适合零样本信息检索比较 | 用小子集校准 Top-K、Recall@K、Precision@K、NDCG 和干扰文档表现 | 不测上传、解析、Chunk、权限、页面或 Agent 行动；各子集许可证需分别核对 | P0 校准 |
| [MTEB](https://github.com/embeddings-benchmark/mteb) | Embedding 模型的多任务评测集合 | 比较候选 Embedding 在检索任务上的基础能力 | 不能证明你的切块、索引、查询路由或最终回答正确 | P1 |
| [MIRACL](https://github.com/project-miracl/miracl) | 多语言信息检索 | 若产品需要中英或多语言问法，可测试跨语言召回 | 公开语料与企业中文文档分布不同；使用前核对目标语言子集 | P1 |
| [Mr. TyDi](https://github.com/castorini/mrtydi) | 多语言问答检索 | 测同义问法、不同语言问法和专名召回 | 中文覆盖和数据许可需单独确认；不测文件处理链路 | P1 |
| [KILT](https://github.com/facebookresearch/KILT) | 检索与下游任务统一格式，并强调证据来源 | 借鉴“检索结果 + provenance + 下游答案”的数据组织方式 | 语料以公开知识为主，不代表企业权限和内部文档 | P1 |
| [Qasper](https://allenai.org/data/qasper) | 长篇论文问答，带证据段标注 | 测长文、跨段落证据和引用回跳 | 学术论文结构与企业文档不同；不直接测上传 UI | P1 |

**选用原则：**当前 V1 只需从 BEIR 选 1–2 个小子集做检索 sanity check；不要一开始引入 MS MARCO 等大规模数据。检索指标应在“原始公开 corpus”和“上传后产品 corpus”分别计算，不能混为一谈。

### 1.2 Parser / 版面 / 表格数据

| 资源 | 覆盖内容 | 对本项目的用途 | 适用条件与限制 | 优先级 |
| --- | --- | --- | --- | --- |
| [DocVQA](https://www.docvqa.org/) | 文档图像问答，含页面和问题答案 | 如果 V1 支持扫描 PDF/OCR，可测页面文字和版面理解 | 若产品只处理文本层 PDF/DOCX，图像集只能作参考；图片答案不等于 Chunk 质量 | 按能力启用 |
| [DocLayNet](https://github.com/DS4SD/DocLayNet) | 文档版面区域标注 | 构造标题、段落、表格、页眉页脚等 Parser 结构用例 | 需要把版面标注转换成自己的“解析文本 + 位置”真值 | P1 |
| [PubLayNet](https://github.com/ibm-aur-nlp/PubLayNet) | 科学文档版面标注 | 补充版面检测和阅读顺序测试思路 | 科学论文分布不等于企业纪要、合同或中文材料 | P1 |
| [PubTables-1M / Table Transformer](https://github.com/microsoft/table-transformer) | 表格检测与结构识别 | 测表头、行列、合并单元格和表格位置 | 需要将视觉表格结果映射到产品最终可检索文本 | P1 |
| [TAT-QA](https://github.com/NExTplusplus/TAT-QA) | 财务表格 + 文本的问答和数值推理 | 测表格与正文联合取证、数字和单位 | 财务领域为主，不应替代自己的业务表格真值 | P1 |
| [FinQA](https://github.com/czyssrs/FinQA) | 财务报告问答和数值推理 | 测数值、单位、计算链和证据段 | 更偏推理/问答，不测上传和索引生命周期 | P2 |
| FUNSD / XFUND | 表单和字段关系标注 | 只有在产品要处理表单、票据、审批单时才值得引入 | 领域与企业知识库一般文档差异很大 | 按能力启用 |

**关键判断：**Parser 的“真值”不是一个总分，而是原始文件中的关键文字、标题路径、表格关系、页码和阅读顺序是否保留。公开版面集可以帮忙覆盖结构类型，但关键字段仍应在自建文档中人工标注。

### 1.3 RAG 回答可信度、拒答与引用

| 资源 | 覆盖内容 | 对本项目的用途 | 不能直接当作什么 | 优先级 |
| --- | --- | --- | --- | --- |
| [RAGTruth](https://github.com/ParticleMedia/RAGTruth) | RAG 回答中的幻觉/不受支持断言标注 | 借鉴断言级接地、幻觉 span 和错误分类 | 不能替代企业文档中的数字、版本和权限真值 | P0 借鉴 |
| RGB（Retrieval-Augmented Generation Benchmark） | 噪声鲁棒性、无答案拒答、信息整合、反事实鲁棒性等方向 | 设计无依据拒答、干扰上下文和反事实文档用例 | 数据与实现版本需在官方发布页核对；不测 Web 上传体验 | P0 借鉴 |
| RAGBench | 上下文相关性、回答接地等 RAG 评测样例/标注 | 借鉴 context relevance / faithfulness 的拆分方式 | 不能用它的聚合分数代替自己的发布门槛 | P1 |
| CRAG（Comprehensive RAG Benchmark） | 含不可回答、噪声和知识时效等更现实的 RAG 场景 | 设计无答案、过时信息和多来源冲突用例 | 公开网页场景与企业私有文档不同；访问条件需复核 | P1 |
| FreshQA / Freshness 类数据 | 关注事实更新和时效 | 借鉴“旧答案看似正确但已过期”的测试方式 | V1 若没有版本/更新语义，可先记录风险，不强行判定通过 | P1 |
| [ARES](https://github.com/stanford-futuredata/ARES) | RAG context relevance、answer faithfulness、answer relevance 的评估流程和合成数据 | 借鉴自动评测与人工校准的组合 | ARES 是评估方法/工具，生成数据不能直接成为业务真值 | P1 |

**本项目必须保留的四个独立判定：**事实值正确、答案接地、引用支撑、无依据拒答。只看“回答是否通顺”会漏掉最危险的问题。

### 1.4 更新 / 删除 / 持续 RAG

| 资源 | 覆盖内容 | 对本项目的用途 | 当前处理方式 |
| --- | --- | --- | --- |
| [CRUD-RAG](https://github.com/RUC-NLPIR/CRUD-RAG) | Create / Read / Update / Delete 等持续知识库变化场景，偏中文企业式问题 | 借鉴重传、更新、删除传播和旧知识残留的用例设计 | V1 若尚未承诺版本和删除，作为风险集保留；U2b 再纳入发布门槛 |

CRUD-RAG 的价值不在于直接复制它的业务内容，而在于把“知识会变化”作为独立测试轴。第一版至少要记录：重复上传的语义、处理失败重试是否重复入库、源文档删除后是否仍能问出旧内容。

### 1.5 不是测试集的工具

以下项目有助于执行或评分，但不要把工具自带的示例当成 Golden Dataset：

- [Ragas](https://github.com/explodinggradients/ragas)：评估指标和测试集生成工具。
- [RAGChecker](https://github.com/amazon-science/RAGChecker)：细粒度 RAG 诊断指标。
- DeepEval、Phoenix、Langfuse 等：评估/追踪/观测能力。

正确关系是：**本项目定义真值和判定规则，工具负责计算或收集证据。**

### 1.6 UX / 信息架构

目前没有一个成熟的公开 benchmark 能直接判断“知识库首屏是否让第一次用户知道下一步、技术参数是否过多、处理状态是否易懂”。这部分必须使用任务脚本、观察记录和截图/录屏，不能用 RAG 分数替代。

## 2. 开源资源如何接入，而不是喧宾夺主

### 2.1 采用等级

| 等级 | 含义 | 处理方式 |
| --- | --- | --- |
| A：直接校准 | 数据结构和目标与当前层接近 | 小规模导入，保留原始 ID、qrels、证据和许可证记录 |
| B：借鉴设计 | 方向相关，但语料/领域不匹配 | 只复制用例维度、Rubric 或生成方法，不直接拿平均分做门槛 |
| C：暂不采用 | 与当前能力差异过大或成本高 | 记录原因，避免为“看起来完整”增加无效工作 |

### 2.2 当前推荐组合

| 目标 | 推荐开源资源 | 本项目自建部分 |
| --- | --- | --- |
| 检索基础校准 | BEIR 小子集；必要时 MIRACL/Mr. TyDi | 中文企业术语、编号、人名、项目干扰和实际 Chunk qrels |
| 文档结构 | DocVQA / DocLayNet / PubTables-1M（仅在能力相关时） | 支持格式的标题、列表、表格、中文混排和损坏文件 |
| 回答可信度 | RAGTruth、RGB、RAGBench 的断言/拒答维度 | 任务 A 真值、引用位置、旧值、新版和禁止归责断言 |
| 生命周期 | CRUD-RAG 的 Create/Update/Delete 维度 | 真实产品的重复上传、重试、刷新、删除和可检索时延 |
| UX | 无需引入外部集 | 7 个首次使用任务 + 观察记录 |

### 2.3 开源资源登记表（下载前填写）

任何外部数据进入测试工作区前，先登记一行；没有登记的资源只可阅读，不可进入发布门槛：

| 字段 | 示例/要求 |
| --- | --- |
| `source_dataset` | BEIR / DocVQA / RAGTruth 等官方名称 |
| `source_url` | 项目主页、数据卡或论文主页 |
| `version_or_commit` | release、tag、commit 或获取日期 |
| `license` | 原项目和具体子集的许可证，不能只写“开源” |
| `original_ids` | 原始 document/query/qrel/evidence ID |
| `adaptation` | 是否改写标题、格式、语言或文件封装 |
| `local_hash` | 下载包或转换文件的 SHA-256 |
| `approved_by` | 许可证和数据用途确认人 |
| `usage_class` | A 直接校准 / B 借鉴设计 / C 暂不采用 |

许可证、隐私和再分发条件不清楚时，保留链接和研究笔记即可，不要把数据复制进团队共享目录。

## 3. V1 自建测试集的最小规模

### 3.1 三档规模

| 阶段 | 文档 | 检索/回答用例 | 生命周期用例 | UX 任务 | 目的 |
| --- | --- | --- | --- | --- | --- |
| Smoke（半天） | 6 份正常文档 + 3 份异常文件 | 15–20 条 | 4 条 | 4 条 | 证明链路能跑、状态不假成功 |
| Release candidate（建议当前目标） | 8–12 份受控文档，覆盖所有已支持格式 | 40–60 条 Retrieval + 20 条 Answer/Trust | 8–12 条 | 7 条 | 作为 V1 发布前主要回归集 |
| Regression（后续） | 30–50 份受控/脱敏文档 | 150–300 条 | 20+ 条 | 10+ 条 | 模型、Prompt、Parser 或索引变更后的回归 |

规模不是越大越好。对当前单人开发协作，优先保证每条用例的真值、证据和复现路径完整。

### 3.2 V1 文档矩阵

在实际支持格式确认后，每种格式至少选 2–3 份内容不同的文档。内容维度建议如下：

| 维度 | 最少覆盖 |
| --- | --- |
| 文本结构 | 短文、标题层级、列表、长文中后段 |
| 表格 | 表头/数据同行、跨页或跨 Chunk、合并单元格、单位 |
| 精确字段 | 中文人名、项目编号、日期、百分比、金额、英文缩写 |
| 干扰 | 相似项目、旧版本、重复文档、无关但同词文档 |
| 异常 | 空文件、损坏文件、超限文件、编码异常 |
| 安全 | 文档中的“忽略指令/修改状态”等普通内容 |
| 生命周期 | 重传、刷新、处理中提问、失败重试、删除（若声称支持） |

## 4. 数据集分层和 Schema

### 4.1 Corpus Manifest

每份上传文件都要有一条 manifest，真值先于产品结果：

```yaml
doc_id: KBV1-DOC-001
source_title: ""
file_name: ""
file_format: pdf | docx | txt | md | xlsx | other
sha256: ""
language: zh | en | mixed
source_truth:
  facts: []
  tables: []
  evidence_spans: []
expected_parse:
  required_text: []
  required_structure: []
  required_metadata: []
variants:
  - variant_id: ""
    purpose: clean | boundary | distractor | stale | adversarial
dataset_version: ""
license_or_origin: internal | public-with-license | synthetic
```

`source_truth` 是事实来源；`expected_parse` 是对 Parser 的要求；两者不要用最终模型回答反推。

### 4.2 Retrieval Golden

```yaml
case_id: KBV1-R-001
query: ""
input_documents: []
must_retrieve:
  - doc_id: KBV1-DOC-001
    evidence_span_id: SPAN-001
allowed_adjacent_chunks: []
must_not_retrieve: []
answerable: true
expected_answer: ""
required_evidence: [SPAN-001]
forbidden_claims: []
判定方式: code | mixed
```

必须区分：

- 目标文档在库中但没有进入 Top-K：索引/检索问题。
- 目标 Chunk 进入 Top-K 但没有进入 Agent 上下文：上下文拼装问题。
- 证据进入上下文但答案错误：生成/引用对齐问题。

### 4.3 Answer / Trust Golden

```yaml
case_id: KBV1-A-001
query: ""
answerability: answerable | unanswerable | insufficient_context
expected_facts: []
required_evidence: []
acceptable_answer_forms: []
forbidden_claims: []
must_cite: true
must_refuse_if_missing: true
judge_dimensions:
  - factual_value
  - groundedness
  - citation_support
  - uncertainty_or_refusal
```

答案正确但引用错误，仍判不通过；答案语言流畅但写入了来源中不存在的数字，按高风险问题处理。

### 4.4 UX Task Set

```yaml
case_id: KBV1-UX-001
task_goal: "第一次使用者上传一份文档并提出一个问题"
starting_state: empty_knowledge_base
success_criteria:
  - 找到上传入口
  - 选择支持格式
  - 理解何时可以提问
  - 找到答案来源
observe:
  - first_click
  - hesitation
  - wrong_action
  - need_for_explanation
evidence: screenshot | recording | notes
```

UX 结果至少写清“用户卡在哪里、当时误解了什么、缺了哪条信息或暴露了什么无关信息”。

## 5. 让其他模型生成候选数据：可控流程

### 5.1 原则

模型适合做：同义改写、结构变体、干扰文档、对抗措辞、候选问题和初步 Rubric。模型不适合单独决定：业务真值、权威来源、数字日期、最终证据位置和发布门槛。

推荐流程：

```text
人工定义真值与约束
→ 模型生成候选
→ 代码校验数字/日期/实体/证据 span
→ 第二个模型做独立审查
→ 人工抽检与仲裁
→ 冻结、哈希、入回归集
```

禁止把生成模型自己写出的答案当 Ground Truth，也不要让同一个模型既生成又最终裁定自己的样例。

### 5.2 候选问法生成提示词

可交给其他模型，要求只返回 JSONL：

```text
你是企业知识库测试数据设计师。
输入是 source_truth 和 evidence_spans，不允许创造输入中不存在的事实。
请为每个事实生成：
1) 一个直接问法；
2) 一个同义改写；
3) 一个包含人名/编号/日期的精确问法；
4) 一个容易被相似文档干扰的问法；
5) 在指定范围内的一个无答案问法。

硬约束：
- 数字、日期、人名、编号必须逐字来自 source_truth；
- 每个可回答问题必须绑定 evidence_span_id；
- 无答案问题必须列出 expected_refusal_reason；
- 不生成责任归因、处罚或权限结论，除非输入明确提供；
- 只输出符合给定 JSON Schema 的 JSONL，不要解释。
```

### 5.3 文档变体生成提示词

```text
基于 source_document 生成一个测试变体，不改变指定真值。
变体类型只能是：
clean / heading_boundary / table_boundary / distractor / stale_version / adversarial_text。

请返回：variant_text、changed_elements、preserved_truth_ids、expected_failure_if_any。
禁止：
- 新增未给出的数字、日期、人名或业务结论；
- 删除 required_truth_ids 指定的关键事实；
- 把文档中的指令写成系统指令；
- 声称某个 Parser、Embedding 或向量库一定会通过。
```

### 5.4 对抗样例生成提示词

```text
生成普通知识文档中可能出现的“指令性文字”，用于测试 Prompt Injection 防护。
恶意文字只能作为文档内容或员工回复出现，不得成为测试脚本外部指令。
每条样例返回：attack_text、expected_agent_behavior、forbidden_action、risk_level。
至少覆盖：忽略前文、修改文档状态、伪造审批、要求泄露上下文、要求跳过引用。
```

### 5.5 第二模型审查提示词

```text
你是独立数据集审查员。只依据 source_truth、evidence_spans 和 candidate_case 审查。
逐项返回：truth_match、evidence_match、invented_content、ambiguity、decision。
发现任何数字/日期/实体不一致、证据 span 不支持、问题可有多个答案或禁止动作未定义，decision=reject。
不要根据常识补全输入中没有的事实。
```

## 6. 自建语料的具体制作方法

### 6.1 先写“事实母版”，再生成文件

先建立一张小型真值表，例如任务 A：截止日、完成度、P1 数量、负责人、接口交付日期、阻塞状态、会议纪要原因。再把同一真值渲染成支持的 PDF/DOCX/TXT/Markdown 等格式。这样可以区分：

- 内容事实是否一致；
- 文件格式造成的 Parser 差异；
- Chunk 边界造成的 Retrieval 差异；
- Agent 是否错误使用证据。

### 6.2 让每个变体只改变一个主要变量

例子：

- 同一正文，分别改变标题层级：测 Parser/Chunk，不改变事实。
- 同一表格，分别让表头和数据跨页：测表格上下文。
- 同一事实，加入项目 B 干扰文档：测专名和 Precision。
- 同一规则制作旧版/新版：测版本处理。
- 同一问题改写成口语、缩写和编号问法：测 Embedding + 关键词召回。
- 同一文档加入“忽略之前指令”：测安全护栏，不改变真值。

### 6.3 公开数据转成上传文件时的适配规则

如果要把 BEIR 或其他公开 corpus 转为产品可上传文件：

1. 保留 `original_dataset`、`original_doc_id`、原始文本和许可证信息。
2. 不修改原文事实；只增加必要的标题、文件名或测试元数据，并明确记录改动。
3. 把原始 qrels 映射到产品生成的 `doc_id` / `chunk_id`。
4. 公开数据只作为专项校准集，不与内部真值混成一个无法追溯的总分。
5. 下载前记录数据集版本、来源 URL、许可证、哈希和获取日期。

## 7. 目录、版本和证据归档

建议在项目外或测试工作区建立如下结构；具体路径由团队决定：

```text
kb-v1-dataset/
  sources/             开源资源说明、许可证、版本和原始 ID 映射
  corpus/              原始上传文件与格式变体
  truth/               真值表、证据 span、文件哈希
  retrieval/           queries、qrels、正负例
  answer/              期望答案、引用、拒答和禁止断言
  lifecycle/           重传、更新、删除、失败恢复用例
  ux/                  任务脚本、观察记录、截图/录屏索引
  generated/           模型生成的未审候选
  verified/            通过代码和人工审查的候选
  frozen/              已冻结、可回归的版本
  runs/<build>/        页面状态、解析结果、Top-K、Prompt、回答和指标
  defects/             缺陷报告与回归结果
```

每次运行至少保存：

- build、Parser、Embedding、Rerank、Prompt 和数据集版本；
- `upload_id`、`document_id`、`processing_job_id`、`chunk_id`、`retrieval_trace_id` 或等价字段；
- 原始文件、解析文本、Top-K、实际 Agent 上下文、回答、引用和截图；
- 失败时的错误码、状态时间线和复现步骤。

## 8. 当前 V1 的执行顺序

### 第 1 步：确认产品契约

先向开发确认支持格式、大小限制、处理状态、重传/删除语义、引用能力、无答案行为和可提供的中间日志。未承诺的能力标为“待确认风险”，不要直接判缺陷。

### 第 2 步：冻结最小自建集

先完成 8–12 份受控文档、40–60 个 Retrieval/Answer 用例和 7 个 UX 任务。任务 A 继续作为主案例，并为每条关键事实标注来源位置。

### 第 3 步：跑 P0 核心链路

顺序固定为：

```text
上传状态 → 解析文本 → Chunk/元数据 → 索引存在性
→ Top-K → Agent 上下文 → 答案事实值 → 引用支撑/拒答
```

任何“页面显示成功但不可检索”“关键表格/数字丢失”“有证据仍编造”“引用无法回跳”的问题先处理。

### 第 4 步：加入少量开源专项集

- Retrieval：BEIR 小子集，检查指标计算和检索日志。
- 文档结构：只有在 V1 支持相关能力时才加入 DocVQA/表格集。
- 回答可信度：用 RAGTruth/RGB 的错误维度补无答案、干扰和反事实样例。
- 生命周期：保留 CRUD-RAG 维度，待产品承诺更新/删除后纳入门槛。

### 第 5 步：冻结回归和回填长期文档

将稳定用例回填到文档 3 的 L2a、文档 4 的 Retrieval/Assessment、文档 5 的 retrieval-golden，并把真实 bad case 加入下一版数据集，而不是覆盖原有样例。

## 9. 当前不建议做的事

- 不要为了追求数据量下载整个 MS MARCO、BEIR 全集或所有文档图像集。
- 不要把 Embedding 模型榜单分数当作产品检索质量。
- 不要让模型自由编造“企业真值”、黄金答案或引用位置。
- 不要用 LLM-as-Judge 单独判数字、日期、权限和引用是否存在。
- 不要把未实现的 ACL、版本失效或删除传播写成“已通过”。
- 不要把 UX 评审简化成页面截图审美；必须用任务、行为和恢复路径记录。

## 10. 数据集到指标的映射

| 测试层 | 推荐输出 | 第一版判定重点 |
| --- | --- | --- |
| 上传/处理 | 状态时间线、错误码、任务 ID | 成功/失败不混淆；失败可恢复；无静默假成功 |
| Parser | 原文与解析文本的关键字段对照 | 关键文字、标题、表格行、数字和日期不丢失 |
| Chunk | Chunk 文本、位置和元数据 | 证据不被切断；来源和位置可回跳 |
| Embedding/索引 | 索引存在性、重复数、版本信息 | 处理完成后可检索；重试不重复；旧块行为可解释 |
| Retrieval | Top-K、qrels、分数和延迟 | P0 必须命中；专名/编号不漏；干扰不过度压过目标 |
| Agent 使用 | 答案、断言、引用、拒答 | 数字/日期正确；断言有证据；引用支持；无答案不编造 |
| UX | 任务完成、耗时、卡顿、误操作 | 首次用户能完成主路径；状态和下一步清楚；高级参数不挡路 |

不要把所有层压成一个总分。一个关键数字丢失或一次无依据的确定性回答，即使平均分很高，也可以单独阻塞发布。
